## Purpose
Every leaf component in `components/page/**` and the listed `features/**` folders declares its own `export interface XxxProps` right above the component function, in the same file — there is no shared props-catalogue module. The three exemplars (`AcBreakdown`, `BaseRow`, `CodeBlock`) show the recurring shape: a handful of required data fields, one or two optional presentation knobs with sane defaults, and an optional trailing `className?: string` so the caller can compose Tailwind utility classes via `cn()` without the component hardcoding layout.

## Convention
Folder: apps/dashboard/src/components/page/**, apps/dashboard/src/features/economy/**, apps/dashboard/src/features/telemetry/PhaseStation/**, apps/dashboard/src/features/telemetry/PipelineTimeline/**, apps/dashboard/src/features/workspace/** · Extension: .tsx · Files of this role in this subproject: 37
`XxxProps` is exported (not a private local type) so a parent can re-use it for typed prop drilling. Optional fields carry inline defaults at destructuring time in the function signature (`chevron = false`, `lang = "plain"`) rather than `??` inside the body. `className?: string` is the near-universal last field, merged via `cn(...)` from `@/lib/utils`, never string-concatenated. Components stay pure/presentational — data fetching happens in a parent or a `hooks/useXxx`, never inside the props-typed leaf.

## How to apply
A new presentational component under one of these folders gets its own directory (`ComponentName/index.tsx`) exporting `export interface ComponentNameProps { ...; className?: string }` immediately above `export function ComponentName(...)`. Reuse existing primitives (`cn`, shared atoms like `StatPill`) rather than re-implementing layout chrome that `components/page/README.md` already standardises.
